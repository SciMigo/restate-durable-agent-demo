The model call you pay for twice

Crash a weather agent, watch its retry, and count the model calls. Each card runs one complete experiment; no command copying or directory changes are needed.

Objective

  • Why: A recovered agent can make a costly decision again if that decision is absent from its journal.
  • By the end: Compare five crash scenarios, identify the missing journal entry, explain the RT0016 mismatch, and describe the limit of a journaled in-flight call.

1Prepare once

Leave Restate running in a terminal with docker compose up -d. Prepare installs this repo’s Python packages into .venv. If Restate was already started for this lab, keep it running.

The local page runs on port 3002, separate from the Temporal labs on port 3000. Use the printed http://127.0.0.1 address.

2Run and observe

Run these in order. The page starts the model stub and agent, kills and restarts the agent at the planned point, then reports the call counts and journal. Only one scenario can run at a time.

1.1 · Baseline

The extra call

Why did a stable model get called three times?

demo.py --agent naive --model stable
1.2 · Divergence

A different answer

Find the RT0016 attempt and the model answer that caused it.

demo.py --agent naive --model varying
1.3 · Paused

It stays different

Watch retries stop. This run can take about 40 seconds.

demo.py --agent naive --model drifted --wait 150
1.3 · Variation

Longer restart delay

Change only how long the agent stays down; compare the call count.

demo.py --agent naive --model drifted --wait 150 --restart-delay 9
1.4 · Fix

Journal the decision

Find the Run call model entry and compare the count with 1.2.

demo.py --agent journaled --model varying
1.5 · Limit

Kill it mid-call

Predict the count before the result reaches the journal.

demo.py --agent journaled --model stable --kill-during model
1.6 · Optional

Repair a stuck invocation

Compare resume, kill, and restart-as-new for an already paused run.

What you learned

  • Compare an unjournaled decision with a decision recorded as a durable step.
  • Read the call counts and journal together to explain a replay mismatch.
  • Identify the remaining risk when an external call finishes before its result is recorded.

Questions you should be able to answer

  1. Which journal entry is missing from the naive run, and what does that cost after a crash?
  2. Why does the varying answer cause RT0016, while a stable answer does not?
  3. Why can the mid-call experiment still call the model again after adding ctx.run_typed?
  4. What extra protection would a payment API need before you retried its call?
